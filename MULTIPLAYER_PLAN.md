- **M8 done (2026-10-24):** measured, tuned, tested.
  - **What the relay bills** (`tests/relay_bandwidth.tscn` with `tools/perf/turn_meter.py`, a UDP forwarder between each peer and Cloudflare's TURN that counts what the relay sends each side; live hub, 45 s windows, 144 fps): Cloudflare bills its egress to each TURN client, TURN framing included, so a packet is billed once. Every relayed packet carries 70-80 bytes of framing (TURN ChannelData, DTLS, SCTP), and SCTP acknowledges the other side's packets, adding 25-35 packets a second each way, so the game's own bytes are about 40% of the bill. Billed MB per player-hour: snaps 40 (31 Hz) 50 / 63 / 72 in 4 / 8 / 12-player matches; snaps 42 (41.7 Hz) 56 / 72; snaps 20 42, 30 47, 63 72 (4 players); 30 packets up 44, 125 up 60. Control traffic (refreshes, consent checks) is negligible, and no data went as Data indications (channels bind).
  - **Snapshot timing:** the server runs 8 ms frames and sends on the first frame at least 1000 / snaps ms after the last, so snaps 40 is 32 ms (31 Hz) and 42 is 24 ms (41.7 Hz, Quake Live's cadence). Others are drawn about one interval + 5 ms + Interpolation behind the newest snapshot.
  - **Defaults** (`Q3NetFeed.SNAPS` 42, `MAXPACKETS` 60, used by every join): 42 shows other players 8 ms fresher than 40 for 12% more relay traffic; 60 packets a second keeps commands waiting about 10 ms (30 would save 13% and add 7 ms; 125 would cost 19% more).
  - **Fixed on the way:** a joining client stopped making the movement commands a primed client needs at its first (not-active) snapshot, so a resent gamestate or a lost packet left it loading forever under latency (`q3_netclient.c`); a host fetched relay credentials every 45 minutes whether or not anyone joined, which the guard charges 5 GB each (an always-on dedicated server would have paused relayed play for everyone within 5 days); now only when a join asks and the last ones are 45 minutes old; a dedicated server keeps its status, commands, stop file and key beside its config, so `dedicated_test` no longer overwrites the menu's Dedicated Server settings.
  - **How it plays on a bad link** (`net_lag_test`, 120 ms round trip, up to 20 ms jitter, 5% loss each way): joins, keeps playing, about 12 mispredictions over 1 unit a minute (Quake 3's `cl_packetdup 1`: two packets lost in a row lose commands; knockback adds its own) and 12% of frames draw others ahead of the newest snapshot. On a perfect link: no mispredictions after the join, 9% drawn ahead (see Open).
  - **Tests:** `tests/net_lag_test.tscn` (two processes: a dedicated server child, Gameplay joining over WebRTC through `Q3LagTransport` latency, jitter and loss), the self-test's net check (the loopback at 80 ms and 5% loss, rcon included), `relay_bandwidth` (live relay; run by hand).
  - **Client clock (fixed 2026-10-24):** the clock judges "almost past the newest snapshot" by itself (CL_SetCGameTime), so Interpolation is a real delay again: others drawn ahead of the newest snapshot on 0% of frames on a perfect link (was 9.7%), 1-5% on the harsh one (was 12-20%). The jump after joining is gone (0-11 units, was 280-570): Gameplay loads the map at the gamestate while `Q3Net.hold_entry` keeps the client out of the world (Quake 3 loads before it enters), a correction in the first 1.5 s after entering snaps instead of easing, and a dedicated server stays awake after a map loads until its bots are in (adding one stalls the server about 0.8 s). `cl_packetdup 2` was tried and made no measurable difference; it stays 1. Mispredictions on the harsh link swing 4-35 a minute with the fighting, all small (worst about 20 units).
  - **Usage guard (built 2026-10-24, not deployed):** with `TURN_ANALYTICS_TOKEN` (Account Analytics: Read, on the account holding the TURN key) and `TURN_ACCOUNT_ID` as Worker secrets, the hub reads the relay's real egress every 2 minutes while credentials live (`callsTurnUsageAdaptiveGroups`), revokes any credential sending over 100 KB/s (a host's over 500), stops new credentials at 90% of the budget and revokes every live one at 100%; what the analytics can't see yet counts at its worst case, so a broken token fails safe. Credentials last 12 hours in this mode (connections are sure of 11+), 1 hour without it. 30 mints an hour a player, 300 every 10 minutes in all. `/admin/relay` shows the mode, the real and estimated GB, errors and revocations. Test: `node test/relay_guard.mjs` (a mock of Cloudflare's APIs and its own `wrangler dev`); it passes, except that local workerd loses 3-4 requests a run while the check runs every 1.5 s (none with checks off); the guard finishes cut-short revocations at the next check and joins retry, but whether production loses any is unknown. The local workerd's lost requests were left unexplained (stopped 2026-10-24; local only as far as anyone has seen).
  - **Credential handover (built 2026-10-24):** the relay drops a connection shortly after either side's credentials expire, so 10 minutes before the earlier of the two (`Q3RtcTransport.expires_at`: its own credential's `at` + `ttl`, and the host's `expires_in` from `net_accepted`) the joiner fetches fresh ones and sends `net_join {renew, gen}`; the hub forwards it over the existing link (no listing checks), the host answers on its current credentials and opens a second connection for that player beside the first, signals tagged with `gen` (`Q3RtcLink`), and both sides swap when it opens: the host feeds the new channel into the same engine peer, so id's netchan never sees a change. A failed renewal leaves the old connection and tries again a minute later. Test: `rtc_loopback_test` forces one halfway (`renew_now()`): both sides swap, the slot stays, every snapshot after it is exact.
  - **Open (Ozmium's call):** the guard charges worst cases (0.7 GB a player credential, 5 GB a host's), about 10x real use, yet doesn't bound abuse: a credential taken out of the game can push 50-100 Mbps through Cloudflare for its hour. Cloudflare's analytics (`callsTurnUsageAdaptiveGroups`, egress per credential, 30 s behind) and its revoke endpoint would make a guard on real usage; that needs an Account Analytics API token. And a relayed connection ends when either side's credential expires (Cloudflare drops it shortly after), so a connection is sure of only about 15 minutes while credentials are reused for 45; it needs a handover to fresh credentials.

Real online matches, built on the decisions in PLAN.md "Multiplayer and online services" (all from 2026-10-22/23):
- Players host matches on their own PCs, peer-to-peer over WebRTC.
- Every internet connection goes through Cloudflare's TURN relay, so no one sees another player's IP.
- Matches are found in the closest region first, and players can pick a region.
- Anyone can run an always-on dedicated server.
- Ranked is peer-to-peer for now: a result counts only when the players' signed scoreboards agree.

## What exists today (surveyed 2026-10-23)

- **Server side is mostly there.** q3core compiles ioquake3's real server networking unmodified: netchan, `msg.c` delta snapshots, Huffman, `SV_PacketEvent`, the connect handshake (`SV_DirectConnect`), and `SV_SendClientMessages`. Nothing feeds it packets: `net_enabled` is 0, nothing calls `Com_EventLoop`, and the only client is the in-process local one (`q3_local_connect`, `q3_host.c:196`), which skips the network entirely.
- **There is no client side.** The build uses `null_client.c`, and no `cl_*.c` or cgame code is compiled. Gameplay reads the live server: `Q3Server.player_state` (the server's ps, not a snapshot), `configstring`, `cvar`, `trace` and `point_contents` on the server's world. `Q3Server.predict` exists but only a test uses it, and other players aren't interpolated between snapshots.
- **`Q3Client` is reusable.** `apply_snapshot` / `animate` / `present` take plain Dictionaries in `Q3Server.snapshot`'s shape, so a network-fed snapshot can drive it unchanged. Its server ties (configstrings, trace, point_contents) move behind one interface.
- **Online backend:** the hub (`online/src/hub.ts`) does friends, parties, presence and leaderboards. It has no match directory, no signaling, no TURN credentials, and the presence `join` field is never filled.
- **No WebRTC anywhere,** and the webrtc-native extension isn't in `godot/addons/`.
- **No dedicated mode.** `Q3MatchSetup.server_type` already lists `listen` and `dedicated`, but nothing branches on it. There's one export preset (Windows), and the q3core build is Windows-only (`sys_win32.c` hardcoded).

## Design

**One protocol: Quake 3's own.** Remote players speak id's real client protocol (getchallenge, connect, gamestate, delta snapshots, usercmds, reliable commands) over a WebRTC data channel instead of a UDP socket. The server stays id's code untouched, so the netcode behaves the way Quake 3's always has, and a later plain-UDP path for public dedicated servers and LAN uses the same packets.

**Transport hook (server).** A new address type, `NA_GODOT`, as a small patch in `tools/q3core/patches/` like the 1.32 reverts. `NET_SendPacket` for that type queues the packet for Godot; Godot hands incoming packets to `SV_PacketEvent`. The API gains `Q3Server.net_receive(peer, bytes)` and `Q3Server.net_outgoing()`.

**Net client (new C in q3core, `src/net/q3_netclient.c`).** A port of the network half of ioquake3's client, without the renderer, sound or cgame VM:
- connect handshake, gamestate, configstrings, `cs` updates, map changes and `map_restart`;
- snapshot parsing with delta against earlier frames (`CL_ParseSnapshot`, `CL_ParsePacketEntities`);
- usercmd packets with delta and the XOR encoding keyed on the server's commands (`CL_WritePacket`, `CL_Netchan_Encode`), and reliable commands both ways;
- pure-pak checksums, so `sv_pure 1` works and clients must have the real paks;
- its own collision world: the client loads the map's BSP through `CM_LoadMap` (players own pak0), traces against it, and clips against solid snapshot entities as cgame's `CG_Trace` does;
- prediction from the latest snapshot's ps with that trace (`CG_PredictPlayerState`), with the error decay cgame uses.

It's exposed as a `Q3Net` class whose results have the same Dictionary shapes as `Q3Server.snapshot`, so `Q3Client` doesn't care where they came from.

**Gameplay on a match source.** Gameplay, the HUD and `Q3Client` read through one interface with two implementations:
- **`LocalMatch`:** today's path (the host, offline matches, the campaign), unchanged in feel.
- **`RemoteMatch`:** fed by `Q3Net`. Other players and items interpolate between two snapshots (`CG_InterpolateEntityPosition`), the local player is predicted, and serverinfo replaces cvar reads.

A net overlay shows ping, loss, jitter and snapshot rate.

**Connecting (WebRTC through the relay).** Godot's official webrtc-native extension (1.2.2, MIT; Godot 4.3+) provides unreliable, unordered data channels.
- The hub mints short-lived Cloudflare TURN credentials per player, and the TURN key stays a Worker secret.
- Both sides gather relay candidates only (`iceTransportPolicy: relay`), and the hub drops any other candidate it forwards.
- Signaling (offer, answer, candidates) goes over the hub WebSocket each player already has open.
- A `Q3Transport` script moves packets between the data channels and q3core, and can add fake latency, loss and jitter for tests.

**Match directory (hub).** Hosts register a listing (mode, map, players, max, region, password flag, game version, ranked flag) and update it over their open WebSocket. The hub tags each listing with the host's region from `request.cf`, and drops it when the host disconnects. Joining looks up the listing, checks bans and password, then starts signaling. Friends' presence gets a real `join` value, so "Join" works from the Friends panel and parties.

**Regions.** As PLAN.md "Regions": home region from `request.cf`, Auto widens to neighboring regions after 60 s, a named region stays strict.

**Ranked (peer-to-peer).** As PLAN.md "Trust":
- Every player's game signs the final scoreboard it received with its identity key.
- The hub applies Elo only when the reports match (all players in a duel, a majority of non-host players otherwise), voids the match otherwise, and keeps a per-host void count.
- The matchmaker picks as host the player with the best connection to the others.

**Dedicated servers.** The same executable run headless (`--server <config>`), with no local client. It has its own identity key, so its listing, name and bans persist. It gets rcon and an admin page in the menu, sleeps its game loop when empty, and can start with Windows. A Linux x86-64 build follows (q3core with `sys_unix.c`, a Linux export preset); Linux ARM64 for Oracle's free tier comes after. Public servers can also take plain UDP and register with dpmaster.

## Decisions for Ozmium

1. **When:** decided: last, after the map editor and replays.
2. **Lag compensation:** id 1.32 has none, so online players lead hitscan shots by their ping, as in the original. Options:
   - **Classic** (recommended to start): exactly id 1.32.
   - **An optional server setting** for hitscan rewind, added later as a server rule, off by default.

- **Hosting:** Cloudflare R2 holds the files, and the existing hub Worker lists, rates and moderates them. R2's free tier is about 10 GB of storage with free downloads, plus about 1 million writes and 10 million reads a month (check the current numbers when building). Past it, cents per GB a month.
- **What's shared:** the map editor's published map. That's its document (a few hundred KB), its thumbnail, and the compiled .bsp and .aas (usually 1-10 MB), so a download plays at once without compiling. Maps name Quake 3's textures but hold none of id's files.
- **Identity:** uploads, ratings and "my maps" are signed with the player's existing identity key (the hub already checks it). No accounts.
- **Moderation:** a report button, an admin takedown through the existing admin endpoints, a size cap per map, and a rate limit per player.
- **Menu:** a Workshop page (browse, search, sort by new and top rated, download, rate, report). Downloaded maps join Create Match like published ones (`Q3MapPublish`, `special: "custom"`).
- **Editor:** "Upload to Workshop" beside Publish, for maps already published.

**Later:** Linux ARM64 build for Oracle (about 0.5 h), collaborative map editing over the same connections (MAP_EDITOR_PLAN.md), dpmaster registration.

## Risks

- **Bandwidth:** the server runs at 125 Hz. Snapshots per client are capped by the client's `snaps` userinfo; the default is set in M8 from measurements, trading smoothness against the relay budget.
- **Host advantage:** the host plays at zero ping, as in any listen server. Host election keeps ranked fair-ish until dedicated servers take it over.
- **webrtc-native on Linux headless:** confirmed in M7 before promising Linux dedicated servers.
- **Build platforms:** a Linux q3core build needs a Linux toolchain (WSL or a CI runner); worked out in M7.
